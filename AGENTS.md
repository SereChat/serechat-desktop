# AGENTS.md

## What this is

SereChat Desktop is the native desktop app for [serechat.com](https://serechat.com): AI chat on the user's own desktop, growing into a multi-purpose agent. Today it has sign-in, a chat screen (sessions sidebar, streaming Markdown replies, attachments, model and reasoning pickers), a coding agent with tools confined to a project folder (long runs with retries and compaction, background processes, a browser it drives with screenshots it can see, the project's `AGENTS.md` and Agent Skills from `.agents/skills`, diffs of file changes that can be reverted), slash commands (`/new`, `/clear`, `/compact`, `/model`, `/init`, `/undo`), image/video/audio generation (`/image`, `/video`, `/audio`), MCP servers whose tools work in every chat (`mcp/`), editing a prompt and retrying the last reply, find in chat (Ctrl/Cmd+F), Spotlight search (Ctrl/Cmd+K), self-updating from GitHub releases (`update.rs`), screen reader support through AccessKit (`a11y.rs`, Windows and macOS), and a settings page.

- API: [Responses API](https://serechat.com/docs/responses) (`POST /v1/responses`, SSE streaming); the server's source is in `../serechat` (`app/inference/api/llms/`). Images must use `image_url: {"url": "data:…"}`; tool calls arrive as `function_call` items; results go back as `function_call_output` items (consecutive calls merge into one assistant turn server-side). Tool outputs are text only (anything else is stringified), so screenshots go back as a user message after the outputs. A stream ends with `response.completed`, `response.incomplete` (`incomplete_details.reason`, e.g. `max_output_tokens`: never run that reply's tool calls) or `response.failed` (`error.code`: retry `server_error` and `rate_limit_exceeded`, compact on `context_length_exceeded`). `: ping` comments arrive every 15 s. Usage includes `input_tokens_details.cached_tokens` / `cache_write_tokens`; `/v1/models` reports `context_window` and cache prices; `max_output_tokens` defaults to the model's maximum. Reasoning input items are ignored, and there is no server-side conversation state.
- Media API: [images](https://serechat.com/docs/images), [videos](https://serechat.com/docs/videos), [audio](https://serechat.com/docs/audio) (`app/inference/api/{images,videos,audio}/`, shared code in `mediaShared.ts`). `GET /v1/{images,videos,audio}` lists models with per-mode `schemas` (`required` params, and `required_files`: the input kinds a mode needs) and a `pricing` string; `POST …/generations` with `"async": true` returns `{id, sparks_used}` (1 Spark = $0.01); `GET …/generations/:id` returns `status` (`queued`/`processing`/`succeeded`/`failed`) and `output.url` (`/api/files/:id` on our origin, needs the token). Failed jobs are refunded. Input files go up first as `multipart/form-data` to `POST /api/files/upload` (`file`, `maxBytes` up to 100 MB), which returns `{fileId}`; generations take them as `file_ids`. The server measures input clips itself (a sent `duration` is display-only): an unreadable clip is `422 media_unreadable`, a failure reaching its measuring service a retryable `502`, and a bad or foreign id `404 file_not_found`, none charged. Once a job is accepted its inputs are no longer needed, so the app deletes them (`DELETE /api/user/files` with `{"fileIds": […]}`); uploads and everything but generated outputs count toward a per-user file cap. `POST /api/assets/:id/cancel` cancels and refunds a job still queued (`409` once it started). `GET /api/user/me` (`account` scope) returns `account.balances`: `sparks`, and the model allowance `usage` of `usageMax` in USD. All three take the bearer token (app token or API key); their errors are `{"error": "message"}` (upload: `{"detail": …}`), not the OpenAI-style object.
- Auth: [OAuth 2.1](https://serechat.com/docs/authentication) as the pre-registered public client `serechat-desktop` (no registration, no secret, no device-code grant). `login.rs` opens `/oauth/authorize` in the system browser (PKCE S256, `state`, `scope=chat media files account`, `resource=https://serechat.com/v1`) with a loopback redirect `http://127.0.0.1:{port}/callback`, checks `state` and `iss`, and `auth.rs` trades the code at `/oauth/token`. Access tokens last an hour; refresh tokens rotate on every refresh, so all clones of a `Client` share one `Auth` whose lock serialises refreshes, and each rotation is stored in order. A `401` refreshes once and retries; a refused refresh (or a second `401`) and a `403 insufficient_scope` return to sign-in. Sign-out calls `/oauth/revoke`. Ask for a new scope by adding it to `SCOPES`: old grants then get `insufficient_scope` and the user consents again.
- MCP: the [spec](https://modelcontextprotocol.io/specification/2026-07-28) is 2026-07-28 (stateless: no `initialize`, `_meta` on every request, `server/discover`, `Mcp-Method`/`Mcp-Name`/`Mcp-Param-*` headers). Real servers still speak 2025-11-25 and older (`initialize` handshake, `Mcp-Session-Id`), so the client is dual-era and probes with `server/discover`; it also falls back to the deprecated HTTP+SSE transport. OAuth follows the spec's authorization pages (RFC 9728 → RFC 8414/OIDC discovery → RFC 7591 registration as `native` → PKCE S256 with `resource`, `iss` checked). The client declares no capabilities. `cargo test -p serechat-desktop live_ -- --ignored` runs the checks against real servers (needs Node).
- Zoom: Ctrl/Cmd `+`/`=`, `-` and `0` zoom the whole UI (`zoom` in config, percent, 50–200). `App::scale` multiplies the display scale by it, so logical pixels grow and every layout follows; any layout cached across frames must key on `p.scale` as well as width.
- Updates: `GET api.github.com/repos/SereChat/serechat-desktop/releases/latest`; assets are matched by the names the release job uploads, and GitHub's `digest` (SHA-256) is checked. The release job fails if the tag isn't `v` + the `Cargo.toml` version.
- Local data: everything lives in `~/.serechat/`: `config.toml`, `sessions/<id>.json` + `sessions/.index.json`, `attachments/`, `projects.json`, `mcp.json`, `mcp-auth.json`. The sign-in's refresh token is in the OS keychain (`keychain.rs`). See `README.md`.

See `README.md` for features, the crate layout and the architecture.

## Hard requirements from the owner

- **Fully Rust-native, custom UI.** Use `winit` + `wgpu` and draw every pixel ourselves. No Tauri, no web views, and no UI frameworks (egui, iced, etc.).
- **Stunning, yet extremely fast.** Performance comes first. Redraw only when something changes, do minimal work per frame, and keep the single-pipeline, single-draw-call renderer.
- **Cross-platform:** it must work on Windows, macOS and Linux.
- **Dependencies are costly.** Add one only if it is truly required and can't reasonably be written by hand. No `thiserror`: write custom error types by hand (`Display` + `std::error::Error`). No `anyhow`, no async runtimes (`tokio`), no convenience crates. Disable default features where possible. OS features go through the tools the platform ships with (see `platform.rs`) rather than new crates.
- **Always use the latest versions** of the dependencies we do use.
- **Cargo workspace:** `crates/serechat` is the API client with no GUI deps; `crates/desktop` is the app.
- **Military-grade code quality, properly documented.** Every public item has doc comments, `clippy::pedantic` stays clean (`cargo clippy --workspace --all-targets`), and there are no `unwrap`s on fallible runtime paths. Non-trivial logic gets a small unit test. Parsers must survive hostile input (bounded recursion, no slicing off char boundaries).
- **Secrets:** never log a token (`Tokens` has no `Debug` on purpose). The API refresh token lives in the OS keychain, never in `config.toml`. Write config files atomically, with `0600` permissions on Unix.
- **Agent safety:** tools resolve every path inside the project root (symlinks included). Writing, editing, running commands and fetching URLs need the user's approval in the chat. Links from replies only open `http(s)`/`mailto`. The one tool outside the project: `use_skill` (offered in every chat, project or not) reads files inside skill folders (`.agents/skills` in the project or home folder), with the same path and symlink checks. `fetch_url` and the browser tools touch no files, so they are offered in every chat too; the file and command tools exist only in a project, and without one the model is told to suggest opening a project folder. Background processes (`start_process`) need approval like commands and are stopped when their chat is deleted or the app exits. The browser tools (`browser.rs`) drive an installed Chrome-family browser with a throwaway profile, never the user's own; `browser_open` (http(s) only), `browser_click` and `browser_type` need approval, while snapshots and screenshots don't. Each chat's tab closes when the chat is deleted, and the browser quits when the app exits. MCP tools (`mcp__<server>__<tool>`, every chat) need approval unless their server marks them `readOnlyHint`; stdio servers are stopped (stdin closed, then the process tree ended) when removed or when the app exits. MCP tokens go only to the server URL they were issued for, are dropped when that URL changes, and OAuth endpoints must be HTTPS (or loopback).
- **Testing:** the owner tests the GUI themselves. Don't drive the app with computer use; `cargo build`, `clippy` and `test` are enough. CI (`.github/workflows/ci.yml`) runs clippy with `-D warnings` and the tests on Windows, macOS and Linux; a `v*` tag publishes release binaries.

## Conventions

- Deliberate shortcuts are marked `ponytail:` with their limit and upgrade path. Current ones: fallback fonts are read fully into memory; no complex-script shaping (Arabic, Indic) or bidi; grapheme clusters follow a practical subset of UAX #29; GIF and WebP attachments have no thumbnails; native pickers run helper processes; the browser's WebSocket client talks only to `127.0.0.1` and skips the `Sec-WebSocket-Accept` check; one lock covers the whole browser, so chats take turns; page outlines skip iframes; the config file uses a flat, string-only TOML subset; the exe icon (`build.rs`, from `assets/icon/`) is embedded for MSVC only; macOS gets its icon from the `.app` and Linux from `serechat.desktop`, both made by the release job from `packaging/`; MCP tool lists refresh on reconnect rather than through `subscriptions/listen`, and only tools are offered (no resources or prompts); an abandoned MCP HTTP request keeps its thread until the server answers; an OAuth issuer's trailing slash is forgiven; Linux without `secret-tool` keeps the refresh token in a `0600` file; screen readers get a flat tree, on Windows and macOS only (Linux's AT-SPI adapter needs an async runtime), and Click is their only action.
- Every file the app writes (sessions, config, projects, `mcp.json`, `mcp-auth.json`), and every keychain write, goes through the `Writer` thread in `app.rs`, in order; reads run on workers. Never write files from the UI thread. (The updater writes the executable it installs on its own thread.)
- Glyphs and image thumbnails live in two 2048² atlases packed by `atlas.rs`, which evicts the least recently drawn shelf when full. Images are drawn with `Painter::image`, which decodes on a worker on first use.
- Screens never touch disk or network: they push `Action`s; the app runs them (on worker threads when slow) and reports back via `WorkerEvent`. Never block the UI thread.
- Colours and sizes live in `crates/desktop/src/theme.rs`. Colours come from the active `Palette` (`p.theme`), never hard-coded, so all three schemes (Dark default, One Dark, Light) keep working. The look is Zed-inspired: flat surfaces, hairline borders, 4–6px radii, one accent, no gradients or glows.
- Text never assumes a font covers it: layouts go through `Fonts::resolve`, which falls back to Twemoji and the system's CJK fonts.
- Screen readers see only what widgets describe: anything clickable or readable that is drawn by hand (not with `button`, `switch` or `text_field`, which describe themselves) calls `ui.describe(|| Node::new(role, rect, label))` while it draws. The closure runs only while a screen reader is connected. A control shown only on hover is still described (see `hover_button` in `chat/messages.rs`): a screen reader click moves the mouse onto it.
